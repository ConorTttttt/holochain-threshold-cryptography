## Independently verified findings and remediation

### S1-H01 — Default development custody cannot protect shares from disk or same-UID compromise

- **Severity / disposition:** **HIGH, OPEN, BLOCKING for real custody**; pre-existing environmental design limitation, not introduced by the Stage 2C coordinator patch.
- **Exact source:** `crates/mpc-dkg-worker/src/node_service.rs:199–218` (both `ipc.key` and `storage.key` written under `state_dir`; development anchor provisioned beside it); `crates/mpc-runtime/src/custody.rs:363–387` (loading the local master key, anchored journal); `crates/mpc-runtime/src/lib.rs:315–358` (share encryption and decryption with that key); `crates/mpc-runtime/src/chain.rs:197–221,240–267` (authenticated *software* anchor). Optional separated-layout controls exist in `crates/mpc-runtime/src/custody.rs:114–160` and Phase 7 documentation, but are not the node's default provision path.
- **Affected security property:** Confidentiality of an individual FROST share under offline host compromise; inability to reverse prior signing/nonce state by a whole-disk rollback. Compromise of fewer than the threshold shares does **not**, by itself, forge group signatures.
- **Independent supporting evidence:** `node_service::provision` generates `state_key` and writes it as a regular private file in the very directory holding the encrypted journal. File mode 0600 protects against *other UIDs*, not against an attacker who can read the disk, a process with that UID, or root. The anchor is an authenticated append-only-format file, **not** a hardware monotonic counter; restoring a snapshot that contains both journal and anchor can restore an earlier signed state. `docs/V040_PHASE7_CUSTODY_HARDENING.md:255–271,327–345` independently acknowledges these limits as an earlier project claim.
- **Exploitability assumptions:** Offline stolen disk image containing both key and journal, or code with custody-UID/root access; whole-volume/VM snapshot control for rollback. A network-only adversary cannot exploit this condition through the MPC API. This is a boundary failure **if** the intended production model promises host-compromise or snapshot resistance.
- **Reproduction (safe test plan, not executed):** Provision a disposable default node. Confirm both `storage.key` and `journal.sqlite` are accessible as its owner and the share is decryptable through the documented custody path; restore a *coordinated snapshot of both the journal and the anchor* after a completed operation, then check whether an old lifecycle state becomes available again. Do not use valuable keys or real credentials.
- **Recommended remediation / owner:** Custody implementation agent + integration coordinator. Make the separated custody layout and protected key source *mandatory* for a production profile; keep the master key off an offline-readable node disk (e.g., OS/TPM-bound credential or hardware custody); isolate relay, conductor, signer and custody UIDs; anchor operations to an independently protected append-only or monotonic witness that is outside the same snapshot domain; refuse startup on missing/rewindable production anchors. Declare privileged-host compromise explicitly out of scope if full protection is not feasible.
- **Specific acceptance / regression:** `test_production_layout_rejects_state_directory_key` rejects `KeySource::StateDirectory` in production mode; `test_separated_uids_cannot_read_custody` proves conductor/relay/signer UIDs cannot access the master key or share journal; `test_whole_state_snapshot_rewind_refused` restores both node data and a *local* anchor while leaving the independent witness advanced and demonstrates **failure before nonce preparation or signing**; exercise a completed-signing backup/restore with real fresh test shares. Document threat assumptions and independently witness the external anchor. **Do not close on file-permission-only tests.**

### S1-M01 — Conflicts withheld by Stage 2C are not visible to native consumers, including late conflicts

- **Severity / disposition:** **MEDIUM, OPEN; BLOCKING** for relying on Stage 2C conflict detection as a complete security boundary.
- **Exact source:** `dnas/mpc/zomes/coordinator/mpc/src/lib.rs:320–346,496–525` (`get_inbox` drops conflicts, `get_inbox_slots` reports them); `crates/mpc-dkg-worker/src/signed_call_policy.rs:16–42` (no `GetInboxSlots`); `crates/mpc-dkg-worker/src/conductor_client.rs:189–202` (decodes only plain inbox vector); `crates/mpc-dkg-worker/src/relay.rs:227–265` (polls `get_inbox`); `crates/mpc-dkg-worker/src/signing_signer.rs:100–117` (signer permits plain `get_inbox` only); `crates/mpc-dkg-worker/src/signing.rs:363–378` (seen-set skips repeated slot before comparing payload).
- **Affected property:** Equivocation evidence must reach DKG and signing state machines; previously processed messages must not silently remain authoritative after a later conflict.
- **Independent supporting evidence:** Coordinator returns no conflicting variant via the legacy API. The native signing loop permanently remembers a processed slot but only sees the legacy API and never queries the withheld evidence. Once a variant has been ingested, a late-conflicting committed variant can disappear from subsequent inbox reads without causing the consumer to abort. The relay explicitly rejects *returned* conflicting variants but cannot reject variants it never sees.
- **Exploitability assumptions:** A malicious group member with a valid inbound delivery grant, ability to race two different messages for its own slot under `ChainTopOrdering::Relaxed`; timing such that variant A was observed before B becomes committed. No ability to forge another sender is assumed. The member can already withhold participation; **this is not a demonstrated signature forgery** because FROST package checks, approvals and final verification remain.
- **Reproduction (test to implement):** In an isolated multi-conductor test, pause one of two same-slot concurrent sends before commit; commit A, poll it through the DKG/signing client, then commit B. Assert `get_inbox_slots.conflicts` names both variants and observe that the current old client has no route to that evidence. The repository's earlier Stage 2C tests cover conflict isolation, **not this late-consumer scenario**.
- **Remediation / owner:** Worker/signing + signer-policy + coordinator integration agents. Add authorized `GetInboxSlots` to signed policy, signer profiles, WebSocket decoding and both polling transport interfaces. Abort an operation immediately when a relevant sender/round/sequence is conflicted or over-quota, **including after A was already ingested**. Keep ignoring non-selected senders for signing. Compare rather than unconditionally skip duplicate slots in the signing loop.
- **Specific acceptance / regression:** `late_dkg_conflict_aborts_before_round_two`, `late_signing_commitment_conflict_aborts_and_burns_nonce` and `unrelated_conflict_does_not_poison_other_signers` must pass with a real `get_inbox_slots` result. Verify prior coordinator versions are rejected when the new client requires that extern. Assert signed-call allowlist denies all functions except the intended new read and prior ones; no capability secret is required for this local read.

### S1-M02 — Envelope validation does not bind application/context or exact proposal

- **Severity / disposition:** **MEDIUM, OPEN; BLOCKING for a general cross-app SDK claim**.
- **Exact source:** `crates/mpc-core/src/lib.rs:24–57,136–176,188–210,214–267` (`Envelope` lacks proposal action, application identifier and context digest; validation checks only session ID, protocol, membership, round, payload digest); `dnas/mpc/zomes/coordinator/mpc/src/lib.rs:363–375,416–421` (proposal supplied separately); `crates/mpc-frost-ed25519/src/lib.rs:174–201,251–263` (the *native FROST frame and signed bytes* separately bind proposal/context).
- **Affected property:** Authenticated messages from one accepted ceremony or application must not be valid under another merely because a caller reuses a session identifier.
- **Independent supporting evidence:** Two valid `SessionSpec` values can have equal nonzero `session_id`, `protocol_id`, `protocol_version`, participant roster and round range while differing in `application_id` and `context_hash`. `Envelope::validate_against(B)` checks neither divergent field. A valid A envelope passes B validation when its sender authenticates as that participant. The recipient coordinator stores it under caller-supplied `proposal=B` if B is fully accepted. This is provable by directly following the validation branches; no cryptographic assumption is needed.
- **Exploitability assumptions:** Two accepted proposals with a deliberately reused public 32-byte session ID, shared roster and protocol; an authorised member can submit an A envelope for proposal B. Randomly generated independent session IDs are not expected to collide. FROST's native bound-frame parsing should reject an A frame in B, so **a forged FROST signature is neither established nor claimed**. Other SDK consumers of generic `Envelope` may be more exposed.
- **Reproduction (to implement):** Build `spec_a` and `spec_b` differing **only** in `application_id`/`context_hash` and sharing session ID; assert current `Envelope::new(spec_a,...)` passes `validate_received(spec_b,...)`. With two accepted proposals, exercise `receive_protocol_message` under B with A's envelope and verify storage. In the FROST layer assert `Frame::decode(binding_b,...)` refuses when proposal hashes differ.
- **Remediation / owner:** Core protocol / coordinator + adapter integration agent; any added signed wire field or integrity change requires an explicit DNA-compatibility/new-network decision. Carry proposal action and application/context commitment in authenticated envelope validation, or cryptographically derive the session ID from the full canonical ceremony description and separately enforce uniqueness. Do not pretend a coordinator-only comparison fixes a missing wire field.
- **Specific acceptance / regression:** `cross_application_envelope_replay_is_rejected`, `cross_proposal_envelope_replay_is_rejected` and `same_proposal_valid_envelope_still_delivers` pass in core and coordinator integration. Tests must vary only app/context, only proposal, and both. Verify the unchanged FROST frame/context-binding tests still pass. Any DNA/protocol version migration is recorded and tested, not silently deployed.

### S1-M03 — Fixed per-sender lifetime quota eventually disables a long-lived group

- **Severity / disposition:** **MEDIUM, OPEN lifecycle/availability constraint; conditional release blocker** if users are promised indefinite use of the same group.
- **Exact source:** `dnas/mpc/zomes/coordinator/mpc/src/lib.rs:255–270,272–283,320–346,375–402`; `crates/mpc-dkg-worker/src/conductor_client.rs:189–202` (4,096 client hard limit); `crates/mpc-dkg-worker/src/relay.rs:227–234` (client cap).
- **Affected property:** Continued availability of honest signing, storage-service fairness and predictable rekey horizon.
- **Independent supporting evidence:** For three participants, each of two peers gets a lifetime allotment of 2,048 *stored records* per recipient/proposal. The sender counter is never reset, even as operations complete. An honest operation requires at least two signing-round message slots per participating sender (rounds 4/6), so a group reaches this limit after roughly 1,020 operations once initial DKG traffic is counted. Multiple identical stored copies can also reduce the effective quota if concurrently committed. Stage 2C isolation keeps other senders' capacity intact; it does not provide perpetual group liveness.
- **Exploitability assumptions:** A long-lived proposal and sufficient normal signing activity; alternatively, a member spends its own quota early. A malicious member cannot claim another sender's authenticated allocation.
- **Reproduction (safe):** Seed an isolated recipient chain with a single sender's `quota-1` and `quota` unique envelopes, then request the next honest round-4/6 send. Confirm rejection and that another peer's remaining allocation is still served. Simulate simultaneous duplicate-record commits.
- **Remediation / owner:** Coordinator + SDK lifecycle agents. Document and expose remaining quota; adopt a proactive rekey/re-proposal threshold well before exhaustion, or design bounded/prunable inbox indexes with a versioned storage migration. Never enlarge coordinator limits without also changing native client limits and tests.
- **Specific acceptance / regression:** `honest_sender_quota_exhaustion_triggers_rekey_before_failed_sign` and `malicious_sender_cannot_spend_other_peers_quota` pass at threshold and with concurrency. Provide SDK-visible quota remaining and operator expiry alert; prove a new proposal remains usable while the old exhausted proposal cannot be revived unsafely.

### S1-M04 — A DKG participant can complete locally after peers have aborted

- **Severity / disposition:** **MEDIUM, pre-existing known safety/liveness boundary; historical F2 runtime manifestation NOT independently rerun.** Release condition: an unactivated local descriptor must never be presented as a usable group.
- **Exact source:** `crates/mpc-dkg-worker/src/lib.rs:278–299` (`Finalize` depends on locally received private shares and transcript only); `crates/mpc-dkg-worker/src/relay.rs:319–326` (local `Complete` transition); `crates/mpc-security/src/activation.rs:55–82` (the separate unanimous activation protocol); `crates/mpc-dkg-worker/src/signing.rs:137–171,348–357` (gated signing). Prior report `docs/V040_PHASE6_FAULT_TESTS.md:240–247` records F2.
- **Affected property:** Consistent DKG completion and whether an app may treat a local descriptor as an active threshold key.
- **Independent supporting evidence:** Completing the native FROST protocol and producing a `GroupDescriptor` are local events; they do not demonstrate that every peer saved its share. The Phase 6 report claims that a partial round-3 kill leaves one node locally `completed` while the group is unusable. The activation machine separately requires a matching attestation from **all** session participants; current `run_signing` waits for this, so the complete signing path still has a safety gate.
- **Exploitability assumptions:** Partition, kill or malicious share withholding after only a subset received round-2 secrets; an application erroneously treats `descriptor` / `Reply::Completed` as globally activated. No evidence that current guarded signer accepts an unactivated group.
- **Reproduction (not rerun):** `python3 -I scripts/phase6_faults.py --scenario dkg-kill-r3-partial` in an entirely disposable environment; inspect three journals, then attempt activation and signing with the surviving local descriptor.
- **Remediation / owner:** SDK integration + group activation agents. Provide separate `LocallyCompleted` and `Activated` SDK states and make the signing API accept only durable unanimous activation evidence; expose partial-ceremony status and operator rekey instructions. Do not conflate local FROST completion with reliable broadcast/finality.
- **Specific acceptance / regression:** `partial_round_two_delivery_never_activates_group` asserts one local completion may occur but **zero`ActivatedGroup` tokens**, nonce commitments and signatures occur without all member attestations. `full_dkg_requires_matching_unanimous_activation` succeeds in a healthy 3-member run. The test must inspect real native state, not merely compare a mock descriptor.

### S1-L01 — Signing sequence truncates 256-bit operation ID to eight bytes

- **Severity / disposition:** **LOW, OPEN**; operation namespace collision/availability, not signature substitution.
- **Exact source:** `crates/mpc-dkg-worker/src/signing.rs:89–95` and `:240–251`; `dnas/mpc/zomes/coordinator/mpc/src/lib.rs:320–340,384–393`.
- **Affected security property:** Distinct operation IDs should not contend for the same sender/round/sequence inbox slot.
- **Independent supporting evidence:** `SigningPlan::sequence()` reads only the first eight bytes of the operation ID. Two distinct 32-byte IDs sharing that prefix deterministically map to the same slot; conflicting payloads then provoke `inbox_conflict` or withheld conflicts. The native `Frame` includes full operation ID and rejects cross-operation framing, mitigating safety impact.
- **Exploitability assumptions:** An application/plan author can choose operation IDs or independently scheduled valid operations share a prefix; both use the same proposal, sender and signing round. Routine random 64-bit-prefix collision probability is small.
- **Reproduction / regression:** `distinct_operation_ids_with_same_prefix_have_distinct_slots` should fail today; construct fixed IDs with identical first eight bytes. Replace truncation with a documented, domain-separated 64-bit slot derivation and an explicit collision policy (or migrate to full-ID slot key), then rerun cross-operation and replay tests.
- **Remediation / owner:** Signing + coordinator integration. Until a compatible scheme is deployed, mandate unpredictable unique operation IDs and reject duplicate derived sequences before user approval. **Acceptance:** no silent cross-operation reuse and collision causes a clear pre-sign refusal, with no nonce published.

### S1-L02 — Relaxed-ordering receipt action hashes are not reliable committed action identifiers

- **Severity / disposition:** **LOW, historical live race NOT independently rerun; source-level downstream assumption confirmed.**
- **Exact source:** `dnas/mpc/zomes/coordinator/mpc/src/lib.rs:416–421` (returns `create` hash under relaxed ordering); `crates/mpc-dkg-worker/src/relay.rs:160–167` (checks only 39 nonzero bytes); `crates/mpc-dkg-worker/src/conductor_client.rs:262–269` (trusts returned receipt field). Prior witness `docs/V040_STAGE2C_COORDINATOR_HARDENING.md:86–99,453–455` claims one of two concurrent receipts pointed to a non-chain action.
- **Affected security property:** Ability to use a delivery receipt as reliable evidence of a specific persisted action.
- **Independent supporting evidence:** No consumer verifies that the returned hash corresponds to a subsequently queryable record. The project's own report attributes race-dependent hash mismatch to relaxed chain-top rebasing, but original test logs or a fresh live run were not available here. **Do not claim this race independently reproduced.**
- **Exploitability assumptions:** Concurrent delivery/source-chain rebasing, and a caller using `storage_action` as definitive rather than advisory proof. This is not proven to let an attacker manufacture a successful receipt for an unstored envelope.
- **Reproduction / regression:** Concurrent fan-in Sweettest: for each `Stored` receipt, query author chain by hash and by stable slot; record any hash missing after eventual commit. Fix contract to report a verifiable stable slot/lookup token or explicitly make `storage_action` advisory. **Acceptance:** consumers never assert existence from the receipt hash alone; every signed delivery has a subsequent verified authoritative lookup by slot.

### S1-L03 — Abandoned DKG stays durably “running” after relay exits

- **Severity / disposition:** **LOW, independently source-verified control-flow gap; historical F1 fault NOT independently rerun.**
- **Exact source:** `crates/mpc-dkg-worker/src/lib.rs:341–356` (durable `dkg_abort` runs only when `AuthenticatedController::try_handle` fails); `crates/mpc-dkg-worker/src/node_service.rs:257–267,270–288` (clean EOF returns `Ok(())`, no DKG abort finalisation); `crates/mpc-runtime/src/dkg.rs:94–154` (checkpoint states and abort entrypoint); prior `docs/V040_PHASE6_FAULT_TESTS.md:224–238` records F1.
- **Affected security property:** Durable journal should distinguish abandoned ceremonies from active ones, while refusing all unsafe restart.
- **Independent supporting evidence:** A relay-side timeout or peer failure can terminate the IPC stream without an authenticated worker error. That path returns normally and anchors the journal but need not transition its `running` checkpoint to `aborted`. Current `new_durable` refuses ANY prior checkpoint (`worker/src/lib.rs:324–338`), so the safety property of non-resumption remains.
- **Exploitability assumptions:** Relay timeout/partition/kill that does not cause a worker command failure; primarily audit and operator recovery confusion.
- **Reproduction / regression:** `disconnected_unfinished_dkg_records_terminal_abort` starts DKG in an isolated test, closes the only IPC connection without finalisation and reopens the journal. **Acceptance:** checkpoint is durably `aborted` (or has a distinctly terminal “abandoned” state) before the service exits, and restarting the identical ceremony still fails. Unexpected hard kill remains inferable from a non-resumable unfinished admission marker.

## Verified controls, without overclaiming

1. **Authenticated participant entry:** `coordinator/src/lib.rs:363–375` takes Holochain `call_info().provenance`, not a claimed sender; `mpc-core/src/lib.rs:251–267` checks that it matches the envelope. `mpc-dkg-worker/src/ipc.rs:88–125` uses direction-specific HMAC and sequence checks. These protect against remote sender spoofing under the assumptions of an honest conductor, secret IPC key and trusted local bridge.
2. **Transcript and cryptographic boundaries:** `mpc-security/src/lib.rs:255–271,288–303,385–424` demands authenticated echoed digests and unanimous attestation to a ceremony-bound transcript before producing `VerifiedTranscript`; `mpc-frost-ed25519/src/lib.rs:359–387,408–435` gates Round 2/3 on that evidence. `:226–245` decrypts recipient-specific Round-2 packets with pinned sender key; coordinator's `require_sealed_dkg` is explicitly **structure-only**.
3. **Activation, approval and nonce control:** `mpc-security/src/activation.rs:55–82,99–150` demands authenticated group/intent votes, and `mpc-dkg-worker/src/signing.rs:119–131` compares the operator's own message bytes. `mpc-frost-ed25519/src/lib.rs:593–630` reserves a nonce and commits its public commitment before publication, then consumes its signing authority. `mpc-runtime/src/lib.rs:203–245` persists the one-time slot, with anchor checks in the anchored signing path.
4. **Signer authorisation:** `mpc-dkg-worker/src/signing_signer.rs:49–73,83–173` checks pinned cell, roster, operation, round and result signature; `signed_call_policy.rs:74–155` checks target agent, DNA, function and signed call bytes. `lair_signer.rs` and `socket_signer.rs` remain same-UID-dependent. No source-evidenced bypass of an activated signing intent was established during this review.
5. **Coordinator conflict isolation:** `coordinator/src/lib.rs:320–346` never chooses between two stored distinct variants and preserves unrelated sender slots. Since the code has an acknowledged read-before-write race, this property is only as strong as **every consumer using the correct conflict-aware API** (S1-M01).
6. **Application context:** `mpc-frost-ed25519/src/lib.rs:251–263` domain-separates signatures with exact proposal, session ID, context hash, full operation ID and actual message bytes. The application name is not itself serialized into signed bytes; the signed context depends on callers supplying an application-unique context hash and pinned proposal. The weaker generic envelope boundary is S1-M02. No generic guarantee of safe signing of arbitrary Solana transaction formats is inferred.
