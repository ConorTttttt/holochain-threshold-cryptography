# v0.3.2 security design and evidence boundaries

Version: 0.3.2 **source implementation; uncompiled/untested in this environment**. This release is NOT production-ready and is not a full live native/Holochain orchestration service. Follow the numbered integrations below only after tests succeed.

## 1. Native durable runtime: `holochain-mpc-runtime`

Native **only**, never link `rusqlite` or local secret storage into HDK/HDI Wasm. SQLite `journal_mode=WAL` and `synchronous=FULL`; single `BEGIN IMMEDIATE` transactions prevent concurrent duplicate processing on one persistent database. `apply_received` compares a domain-separated hash of the entire authenticated envelope at the `(proposal, sender, round, sequence)` slot. It invokes only *database-local* side effects in the same transaction; no network or user-visible side effect can be made atomically with SQLite. On duplicates, it does not reinvoke the closure. When two messages reuse a slot with different contents it returns a conflict, not an acknowledgement.

**Trust precondition:** `authenticated_sender` must be derived from a verified Holochain remote caller or independently verified portable signature. A raw `get_inbox` envelope does **not** retain call provenance as portable evidence by itself. Implement a signed-receipt bridge between conductor and native controller before production usage. Unauthenticated client-controlled `authenticated_sender` breaks this guarantee.

## 2. Crash-safe signing nonce order

```
1. Verify accepted session, activated group and approved signing intent.
2. Persist deadline for the operation; reject expired/aborted attempts.
3. Transactionally reserve unique (proposal,group_epoch,operation_id,signer) in SQLite.
4. Generate fresh FROST SigningNonces and public SigningCommitments in memory.
5. Persist commitment digest/state='published' under FULL synchronous transaction.
6. ONLY THEN return/send the commitments to the network.
7. Before signing, check live deadline; enforce exact roster and approved message.
8. Consume nonce in memory on ANY signing attempt. On crash, lose the entire attempt.
```

`ControlledSigner` implements steps 3–8 once the app has done steps 1–2. Nonces are NEVER serialized or stored, and operations cannot be reused after a restart. A failed/aborted signing attempt requires a **new operation ID and new nonce**. The old `Signer` API remains for native prototype tests but is unsafe as a production signing entry point.

**Rollbacks remain a critical blocker:** restoring a stale SQLite database or VM snapshot while resuming the same volatile nonce is outside SQLite's security guarantees. Production deployments must forbid or cryptographically detect rollback, synchronise backups, and never restore a live in-memory signer from a snapshot. A wall-clock deadline is a liveness mechanism and is only as trustworthy as the supplied time source.

## 3. Encrypted group-share storage

Write-once `(proposal, epoch, owner)` row encrypted with XChaCha20Poly1305 and AAD containing proposal, epoch, owner and expected group digest. `open_share` returns a zeroising buffer. The master key is **not derived from a password or Holochain public key**: the caller injects a high-entropy 32-byte secret from a protected key service. Implement Lair/OS HSM provisioning, master-key backup/rotation, and copy/erasure controls. The app must zeroise any temporary serializer buffers it creates for the FROST secret key package.

## 4. DKG group activation

`GroupDescriptor` binds complete `SessionSpec`, exact Holochain proposal ActionHash, group epoch, **completed echo transcript digest**, canonical FROST `PublicKeyPackage` digest, group verifying key, and ordered per-agent public X25519 key-registration ActionHashes.

`GroupActivation::attest(authenticated_sender,digest)` takes a transport-authenticated identity; it requires all *N* members to agree. An `ActivatedGroup` token is non-deserializable and is issued only by `finalize`. `ControlledSigner` validates it against the actual FROST `PublicKeyPackage` bytes before allowing signing. DHT `GroupActivationAttestation` records establish Holochain authorship but **do not prove** the creator ran FROST or actually possesses a key; controllers must confirm DKG state independently.

These tokens are native LOCAL trust evidence, NOT portable publicly verified signatures; implement native signature verification or transport-provenance preservation to reconstruct tokens safely across hosts/restarts. Likewise, the descriptor construction does not cryptographically force a trusted echo transcript: the native orchestrator must supply the `VerifiedTranscript` generated by the echo state machine. Do not accept client-supplied `GroupDescriptor` as trusted.

## 5. Signer authorisation / attribution

`SigningIntent` contains exact operation ID, context-bound message hash, selected signer roster, group key epoch, group certificate digest and explicit profile. `IntentApprovals` requires authenticated approval from ALL selected signers. `ControlledSigner` currently accepts **only** `ContextBoundV1`; `ExternalExactBytesV1` is reserved but deliberately unsupported. The selected roster is compared to the actual signed FROST package before signing. Callers must display human-verifiable operation context and collect real application consent.

`AuthenticatedShareCollector` maps each share to FROST Identifier using the **transport-authenticated** Holochain agent key, detects per-sender conflicts, requires all selected signers and checks FROST group/public-key hashes before calling FROST aggregation. FROST verifies the cryptographic shares; preserve errors and signed evidence separately for attributable abort reports. Never presume a payload's asserted signer ID is authenticated.

## 6. Holochain validation additions

At the END of existing `EntryTypes` and `LinkTypes` (stable historical indices):

- `EncryptionKeyEpoch { proposal,epoch,public_key,previous_binding }`, with author-continuity, epoch+1, same proposal, append-only parent check.
- `GroupActivationAttestation { proposal,epoch,descriptor_hash,dkg_transcript_hash,public_key_package_hash }`.
- `SigningApprovalAttestation { proposal,operation_id,group_descriptor_hash,intent_hash }`.

The coordinator exposes register/query/publish APIs. All are public author-signed **declarations**; they are NOT cryptographic proof of key possession, nor global consistent membership/finality. Conflicting same-epoch forks are possible; consumers must enumerate and explicitly pin rather than choose latest. Public approvals may leak metadata: privacy-sensitive apps should collect authenticated approvals privately instead.

## 7. Integration and adversarial release gates

1. Run `cargo test -p holochain-mpc-security --test group_activation` and `cargo test -p holochain-mpc-runtime --test durable`.
2. Run FROST three-agent native test, including `activated_group_approved_intent_nonce_wal_and_threshold_signing`.
3. Run `npm run build:happ && npm run test:sweettest` after Holochain 0.7 dependencies resolve.
4. Wire native controllers into all **three separate live conductors**. Use actual verified DKG echo transcript and actually pinned X25519 key actions; test encrypted Round 2 and group activation consensus.
5. Fault-inject equivocation, conflicting key epochs, malformed encrypted shares, inconsistent group-key packages, concurrent message races, crash after nonce reservation, crash after commitment burn, replay after restart and partition/rejoin.
6. Review secure identity binding, key possession, backup rollback, metadata, keystore lifecycle and domain-policy approval before shipping any production deployment.

## 8. Scope exclusions

- No complete native daemon, API transport or deployment/service wrapper.
- No end-to-end live three-conductor FROST pipeline (only native simulation + Holochain metadata test sources).
- No OS/Lair/HSM master-key provisioning, physical anti-rollback or verified secure backup/recovery.
- No true portable signed finalisation certificate across trust domains (DHT authored attestations exist).
- No ROAST, proactive share refresh, repair, arbitrary MPC or offline payment double-spend solution.
- No compiler/test run in this authoring container; source is NOT cryptographically audited.

Sources for cryptographic assumptions: [FROST DKG tutorial](https://frost.zfnd.org/tutorial/dkg.html), [FROST signing tutorial](https://frost.zfnd.org/tutorial/signing.html), and [RFC 9591](https://www.rfc-editor.org/rfc/rfc9591.html).
